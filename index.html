What makes it interesting

Four decisions that define the product

This is not a chat window in front of an API. Every claim the app makes about a learner's code is grounded in actually executing it.

Real execution

Python runs on the device

MicroPython compiled to WebAssembly executes learner submissions locally, inside a sandboxed web-content process. Nothing is uploaded, and it works in aeroplane mode.

Deterministic grading

Tests decide, not a model

Submissions are judged by running executable assertions, so pass/fail is exact. A failed assert is dissected to report what the function returned versus what was expected — the one thing a plain AssertionError hides.

Local inference

A 0.5B model in your pocket

An optional 290 MB 4-bit Qwen2.5-Coder, distilled from a 32B teacher and run through MLX on the Neural Engine. The learner's code never leaves the phone.

Verified generation

A fix is executed before it is shown

The model drafts a repair; the app runs that repair against the real tests and only displays it if it passes. When nothing passes, the app says so rather than presenting broken code as an answer.

Architecture

Everything runs locally

There is no server component. The only network request the app ever makes is the one-time model download, and the app is fully usable without it.

What it can and cannot do

A single sample repairs a broken solution about 37% of the time, measured over 517 held-out MBPP candidates built as one-token mutations of correct code. Real learner code is much further from correct, and the rate on it is considerably lower. The number that moved most was not model size but grounding: handing the model the interpreter's actual failure — rather than asking it to judge correctness itself — lifted the verified repair rate from 5.0% to 12.5%.

That gap is the reason the product verifies before it displays. A 0.5B model is not reliable enough to be trusted on its word, so it is never asked to be — the interpreter is the authority, and the model is only ever an explainer.

Engineering decisions

Why it is built this way

  • Executable tests instead of LLM grading. An LLM asked "is this correct?" is confidently wrong often enough to destroy a learner's trust. Running the tests is cheap, exact, and never needs to be second-guessed.
  • The model is optional. It is a 290 MB download the learner chooses. Every lesson, quiz and exercise works fully without it, so the app is not hostage to a feature that some devices cannot run.
  • Inference on-device. No account, no API key, no per-user inference cost, and a privacy guarantee that is architectural rather than a promise in a policy.
  • Infinite loops and unsafe code. User code runs inside a WKWebView, which is a separate OS process with its own sandbox — it cannot touch the app's memory, files or network. A runaway loop hangs only that process; the app times out at 8 seconds and discards the whole web view.
  • 0.5B rather than something larger. It had to fit in a phone's memory budget alongside the app and download over cellular without being absurd. The verification loop is what recovers the quality that size costs.
  • Honest limits in the UI. The model is labelled a beta wherever it appears, and an unverified fix is withheld rather than shown with a caveat — a caveat readers ignore.
  • A problem bank that is actually solvable. MicroPython is a subset of Python; 42 of the original 427 exercises needed standard-library features it lacks. An audit tool runs every reference solution in the real interpreter, and the 42 unwinnable ones were removed rather than left to frustrate learners.
